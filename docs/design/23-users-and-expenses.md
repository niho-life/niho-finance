# 23. 利用者と立替精算（Issue #21 の設計）

v1 は 1 人（IAP で認証したメール）で、許可された人は誰でも何でも書けた（[06 §3.2](06-architecture.md)・[`docs/ops/deploy.md`](../ops/deploy.md) §5）。この文書は v3 で足す 3 つを定めます。

1. 役割（管理者 / 経理 / 閲覧）を持つ複数の利用者と、設定 › 利用者 での追加・役割の変更（§1〜§4）
2. Server Action・route・画面の入口での認可（§3）
3. 社員・業務委託の立替精算 `/expenses`（提出 → 支払 → 仕訳。§5・§6）

承認の段階は作らない（1〜2 人の会社）。役員の立替は従来どおり S2 の口座「役員立替」で扱い、立替精算には載せない（[02](02-accounting-rules.md) §4）。税理士は「閲覧」で報告と帳簿の書き出しだけを見る（§7）。

## 1. 役割

`User.role`（S1 の enum `user_role`）をそのまま使う。画面の表示名は次のとおり（enum の値は見せない）。

| 値 | 表示名 | 想定する人 |
| --- | --- | --- |
| `owner` | 管理者 | 代表。1 人以上を必ず保つ |
| `accountant` | 経理 | 経理を任せる社員・業務委託 |
| `viewer` | 閲覧 | 税理士 |

許す操作（○ = できる）:

| 操作 | 管理者 | 経理 | 閲覧 |
| --- | --- | --- | --- |
| 報告（6 つのタブ）を見る、帳簿の書き出し（freee・弥生・beancount） | ○ | ○ | ○ |
| そのほかの画面を見る（ホーム・明細・取引・証憑・期限・請求・給与・決算・設定・立替精算） | ○ | ○ | — |
| 証憑の書き出し・バックアップ、請求書・給与明細・決算書の PDF / CSV | ○ | ○ | — |
| 登録・訂正・取消、取込、証憑、請求、給与、決算整理と固定資産、期限の完了、勘定科目・税区分・口座・取引先・セグメント・タグ・ルール・定期取引・Stripe の接続、銀行 API の今すぐ同期、決算書の設定、立替精算 | ○ | ○ | — |
| 締め: 月次の締めと戻し（会計期間）、決算の開始と取消、期末の締めと再開 | ○ | — | — |
| 設定の一部: 事業所、会計期間の変更と翌期の作成、証憑の規程、銀行 API の接続・口座の選択・切断（認可の route を含む）、利用者、初期設定 | ○ | — | — |

- 「経理は締めと設定の一部を除く全部」（Issue #21）の「締め」は期間の状態を変える操作（`closeFiscalYearThrough`・`startYearEnd`・`cancelYearEnd`・`closeYear`・`reopenYear`）。決算整理仕訳・固定資産・チェックリストは経理もできる。
- 「設定の一部」は会社の同一性（事業所）・期間の枠（会計期間）・電子帳簿保存法の規程（証憑の規程）・銀行が会社の口座へのアクセスを許す操作（銀行 API の接続。[19-bank-api](19-bank-api.md)）・誰が使えるか（利用者）・初期設定。マスタ（科目・口座など）は日々の経理に要るので経理に任せる。
- 閲覧は Server Action を 1 つも呼ばない（書く画面がない）。読み取りだけの Server Action（プレビュー・候補の読み込み）も経理以上にする。

## 2. 利用者の解決

- actor（`apps/web/lib/actor.ts`、S8）は IAP の署名を検証したメール（小文字）。ローカルは `NIHO_FINANCE_ACTOR`（既定 `owner@example.com`。S1 の seed が作る架空の管理者と同じ。seed していない DB では §2 の最初の管理者になる）。この文字列を `User.email` と突き合わせる。監査ログの actor は従来どおりこのメール（[01 §8](01-domain-model.md)）。
- `currentUser()`（`apps/web/lib/authz.ts`）は 1 要求に 1 回（React の `cache`）、次のどれかを返す。

| 状態 | 条件 | 扱い |
| --- | --- | --- |
| 登録済み | `User` に同じメールの有効な行がある | その行の役割 |
| 最初の管理者 | `User` に行が 1 つもない（v3 を配備した直後・新しい DB） | 管理者として扱う。最初の書き込み（`authorize` が通った時）に `User { email, role: owner }` を足し、監査ログ `user.create`（理由「最初の利用者を管理者として登録」）を残す |
| 未登録 | 行はあるが、このメールの行がない、または無効 | 画面も書き込みも拒む（§3.3） |

- 最初の管理者を DB の migration で作らないのは、公開リポにメールを書けず、migration からは誰が使うか分からないため。いまの IAP の許可リストは代表 1 人なので、最初に書いた人が代表になる。
- 有効な管理者は常に 1 人以上いる（§4）ので、行があって全員が無効という状態は起きない。
- ローカルで役割を試すには、設定 › 利用者 で足したメールを `NIHO_FINANCE_ACTOR` に入れて開発サーバを起動し直す。`.env` に v1 の `NIHO_FINANCE_ACTOR=owner` が残っている worktree は、seed した DB では未登録になる（権限の画面に直し方を出す。`.env` を `owner@example.com` にする）。

## 3. 認可の入口

### 3.1 Server Action

- `authorize(minimum: "viewer" | "accountant" | "owner"): Promise<string>`（`authz.ts`）: 現在の利用者を解決し、役割が `minimum` 以上（owner > accountant > viewer）なら actor のメールを返す。足りなければ `ForbiddenError`（`ActorError` の子。`toActionError` がそのまま `{ ok: false, error }` にする）。
- 拒否したときは何も書かない（監査ログも増えない）。Cloud Logging にだけ `authz.denied`（`minimum` と役割。メールは出さない）を残す。
- export したすべての Server Action の最初の 2 文を `const denied = await authorizeAction(<最低の役割>); if (denied) return denied;` にする（既定は `"accountant"`、§1 の管理者だけの操作は `"owner"`）。読み取りだけの Server Action も同じ。`authorizeAction` は `authorize` を呼び、拒否を throw せず `{ ok: false, error }` で返す（想定内の失敗は throw しない。`lib/action-types.ts`。経理が締めを押してもエラー画面でなくトーストになる）。各 `actions.ts` の `by()`（監査ログの actor）はそのまま。各レーンのファイルには 1 関数 1 行と import だけを足す。
- 認可は入力の検証と repository の呼び出しより前（拒否の理由が入力の誤りに紛れず、検証の途中の読み込みも閲覧に許さない）。
- 単体テストが `"use server"` の全ファイルを読み、export した関数ごとに最初の 2 文がこの形であること、管理者だけの操作が `"owner"` であることを確かめる。新しい Server Action を足したレーンが入れ忘れると落ちる。
- 拒否の文言:
  - 閲覧: 「閲覧の役割では保存できません。必要なら管理者に役割の変更を頼んでください」
  - 管理者だけの操作: 「この操作は管理者だけができます（締め・事業所・会計期間・証憑の規程・利用者）」
  - 未登録: 「このアカウントは利用者に登録されていません。管理者に追加を頼んでください」

### 3.2 route

| route | 必要な役割 |
| --- | --- |
| `/reports/export`、`/settings/export/download`（freee・弥生・beancount） | 閲覧以上 |
| `/api/bank/gmo-aozora/authorize`・`callback`（銀行 API の接続） | 管理者 |
| `/settings/export/download`（証憑・バックアップ）、`/invoices/[id]/pdf`、給与明細の PDF、`/closing/statements/export`、`/api/documents/*` | 経理以上 |
| `/api/health`、`/api/jobs/*` | 変えない（利用者の要求ではない。ジョブは S4 の認証） |

入口は `const denied = await authorizeRoute(<最低の役割>); if (denied) return denied;`。拒否は 403（actor が分からないときは 401）と 1 行の本文（ダウンロードのリンクから開くため「…開けません。ブラウザの「戻る」で前の画面に戻ってください」）。`/api/documents/*` は画面が読む `{ error }` の JSON で返す。

### 3.3 画面（proxy）

- App Router のレイアウトは画面の移動で再実行されない（Partial Rendering）ため、画面の制限は `apps/web/proxy.ts`（Next 16 の proxy。Node の実行環境）で行う。proxy は画面・RSC の読み込み・Server Action・route のすべての要求の前に走る。
- proxy は actor と同じ検証で利用者を解決し（DB の `app_user` を 1 回引く）、
  - 未登録 → `/forbidden?reason=unregistered` に rewrite（403）。
  - 閲覧 → 許す path だけ通す: `/reports` とその下、`/settings/export` とその下、`/forbidden`。`/` は `/reports` へ redirect。ほかの画面は `/forbidden?reason=role` に rewrite（403）。Server Action の POST（`Next-Action` 付き）は 403 の本文だけ返す。
  - 管理者・経理・最初の管理者 → そのまま通す。
  - 本番で IAP の署名がない・検証できない → `/forbidden?reason=unverified`（401）。
- proxy の対象から外すもの: `/_next/*`、`/favicon.ico` などの静的ファイル、`/api/health`、`/api/jobs/*`。
- proxy は「早めに断る」層で、本当の検査は §3.1・§3.2 の入口（Next の推奨どおり、データに近い所で検査する）。proxy が DB を引けないときは通さない（500）。
- 権限の画面 `/forbidden`（アプリの殻の外。ナビなし）: 見出し「この画面は開けません」と理由（閲覧: 「閲覧の役割で開けるのは 報告 と 書き出し だけです」、未登録: §3.1 の文言、未検証: 「ログイン情報を確認できませんでした。画面を読み込み直してください」）、閲覧には「報告へ」のリンク。

### 3.4 殻とナビ

- `(app)/layout.tsx` は役割を `AppShell` に渡す。閲覧の左ナビとスマホの下のタブは「報告」「書き出し」（`/settings/export`）だけ。
- 書き出しの画面（`/settings/export`）は閲覧には「仕訳の書き出し」（freee・弥生）と「beancount」の節だけを出す（証憑・バックアップ・決算書と申告用データ・最近の書き出し〔ほかの人のメールが出る〕を出さない）。題名は「書き出し」、戻るは「報告」へ。
- 報告の中の取引へのリンク（仕訳帳・元帳の行）は閲覧には権限の画面になる。報告の画面は変えない（範囲外。§9）。

## 4. 利用者 `/settings/users`

- 入口: 設定の索引の「利用者」（書き出しの前）。要約は「有効 n 人」。
- 経理は一覧だけを読める（上に「利用者の追加と役割の変更は管理者だけができます」）。管理者は追加・変更ができる。
- 利用者が 1 人もいないとき（§2 の最初の管理者）: 一覧の代わりに「まだ利用者が登録されていません。いま使っているアカウント（<メール>）を管理者として登録します」と CTA「管理者として登録」。押すと §2 の登録をする（ほかの書き込みでも同じ登録が起きる）。
- PageHeader: 題名「利用者」、CTA「追加」（管理者だけ）。
- 一覧（PC の列）: 名前 ・ メール ・ 役割 ・ 操作。並びは 役割（管理者 → 経理 → 閲覧）→ メール。自分の行に「（あなた）」。無効の行は畳み「無効 n 人を表示」で開く（[10 §2](10-settings-and-setup.md)）。スマホは「名前（なければメール）＋役割」の 2 段。
- 名前は一覧の中で直接編集（blur か Enter で保存）。役割は一覧の select で変え、変えた時点で保存する。
- 追加（Sheet）: メール（必須。前後の空白を除き小文字にする。形式を検証）、名前（任意・40 字まで）、役割（既定 閲覧）。CTA「追加」。同じメールがあれば「このメールはすでに登録されています」（無効なら「…無効の一覧から有効にしてください」）。
- 追加したらトースト「<メール> を追加しました」と、一覧の上に案内「このメールで画面を開くには、Google Cloud の IAP の許可リストにも足してください（運用の手順 deploy.md §5）」（閉じられる）。アプリから IAP の許可は変えない（IAM の権限を画面のサービスアカウントに持たせない）。
- 無効にする / 有効にする: 行の操作。無効にした人は次の要求から未登録として扱う（IAP の許可を外すのは運用の手順）。確認ダイアログ「<メール> を無効にしますか。次に画面を開いたときから使えなくなります」。
- 守る規則（`packages/db/src/users.ts` が 1 トランザクションで検査する。advisory lock `users`）:
  - 有効な管理者が 1 人以上残る。最後の管理者の役割を変える・無効にすると「管理者がいなくなるため変えられません。先にほかの人を管理者にしてください」。
  - 自分は無効にできない（「自分は無効にできません。ほかの管理者に頼んでください」）。自分の役割は、ほかに有効な管理者がいれば変えられる（確認ダイアログ「管理者でなくなると、利用者と締めの操作ができなくなります」）。
  - 削除はない（論理削除 = `isActive`）。メールは変えられない（別の人として足し直す）。
- 監査ログ（entity `user`）: `user.create` / `user.update`（名前・役割。`before` / `after` は `{ email, name, role, isActive }`）/ `user.deactivate` / `user.reactivate`。値が変わらない保存は何も書かない。監査ログの画面の対象「利用者」、行の名前は「利用者 <名前（なければメール）>」、action の表示名は 追加 / 変更 / 無効にする / 有効にする。
- schema: `User` は S1 の列（`email`・`name`・`role`・`isActive`）のまま。立替精算の relation だけを足す。

## 5. 立替精算

### 5.1 記録

新しいテーブルを 2 つ足す（Issue #21 の範囲）。

```
enum ExpenseClaimStatus { submitted  paid  void }      // 表示: 未払 / 支払済み / 取消済み

ExpenseClaim（expense_claim）: 1 件 = 1 枚の領収書
  id, claimantId → User（立替えた人）
  spentOn（利用日。計上の仕訳の日付）, amount（税込・正の整数）
  accountId（科目）, taxCategoryCode, segmentId?, partnerId?, description（内容）
  documentId? → Document（証憑）
  status, journalEntryId（計上の仕訳）, paymentId? → ExpensePayment
  voidReason?, voidedAt?, reversalEntryId?（取消の反対仕訳）
  createdBy, createdAt, updatedAt

ExpensePayment（expense_payment）: 1 回の支払（1 人分を 1 つの仕訳で）
  id, claimantId → User, paidOn, walletId → Wallet, walletTransactionId?（照合した明細）
  amount（合計）, journalEntryId（支払の仕訳）
  cancelledAt?, cancelReason?, reversalEntryId?
  createdBy, createdAt
```

- `SourceKind` に `expense`（表示名「立替精算」）を足す。計上の仕訳の `sourceId` は立替精算の id、支払の仕訳は支払の id。
- 未払金（2100）の補助科目「立替精算」を最初の提出で作る（なければ作り、無効なら有効に戻す。監査ログは `sub_account.create` / `.activate`。給与の 〔給与〕 と同じ作り方）。立替えた人ごとには分けない（名前が変わる・人が増えても科目が増えない）。人ごとの残高は立替精算の画面で見る。

### 5.2 状態と仕訳

```
（なし）──提出──▶ 未払 ──支払う──▶ 支払済み
                  │  ◀──支払の取消──┘
                  └──取消──▶ 取消済み
```

| 操作 | 仕訳 | 日付 |
| --- | --- | --- |
| 提出 | 計上: 借方 科目（税込経理なら税込、税抜経理なら税抜＋仮払消費税）/ 貸方 未払金〔立替精算〕 税込 | 利用日 |
| 支払う | 支払: 借方 未払金〔立替精算〕（立替精算 1 件ごとに 1 行）/ 貸方 支払元の口座の科目（と補助科目） 合計 | 支払日 |
| 支払の取消 | 支払の仕訳の反対仕訳（`voidJournalEntryWithOpenDate`。締め済みなら開いている最初の日付） | 支払の仕訳の日付 |
| 取消（未払だけ） | 計上の仕訳の反対仕訳（同上） | 計上の仕訳の日付 |

- 計上の仕訳は「支出」の組み立て（`buildSimpleEntry`、`type: "expense"`、支払元 = 科目 未払金）をそのまま使い、貸方の未払金の行に補助科目「立替精算」を付ける。税区分・セグメント・仮払消費税・経過措置の扱いは取引の支出と同じ（[11 §1](11-transactions.md)）。摘要は「立替精算 <立替えた人> <内容>」。
  - 未払金（2100）は標準の科目表でカードの口座の科目でもあり、支出は口座の科目を支払元に選ばせない。立替精算は 2100 を意図して支払元にするので、組み立ての前に 2100 に紐づく口座を外す（選べる費用の科目の検査は口座を含めたまま行うので、取引の支出と同じ科目だけを選べる）。
  - 取引先（店）は費用の行にだけ付け、未払金〔立替精算〕の行には付けない。未払金は立替えた人への債務で、支払の行に取引先がないため、付けると取引先ごとの未払金の残高が 0 に戻らない。
- 提出で計上するのは、費用を発生した日の期に入れるため（発生主義。月をまたぐ・期をまたぐ立替を正しい期に載せる）。未払のあいだは未払金〔立替精算〕に残高が立ち、支払で 0 に戻る。
- 支払の仕訳の摘要は「立替精算の支払 <立替えた人>（n 件）」、借方の各行は「<利用日> <内容>」。支払の件数は借方の行の数で数える（取消の後も残る）。
- 支払は立替えた人ごと。未払の立替精算のうち選んだもの（既定は全部）を 1 つの仕訳で払う。支払日は選んだ立替精算の利用日以後。支払元は有効な 銀行・現金 の口座（カード・Stripe・役員立替は出さない）。
- 明細から選ぶ: 支払元の口座の未処理の出金で、金額が −合計 のものを候補に出す（任意）。選ぶと支払日は明細の日付になり、明細は「登録済み」で支払の仕訳を指す（監査ログ `wallet_transaction.register`。請求の入金と同じ。[18 §5.2](18-invoicing.md)）。支払の取消で明細は未処理に戻る。これで銀行の明細を取り込んだときに二重に登録しない。
- 証憑: 提出のときに選んだ証憑を計上の仕訳に紐づける（`linkDocument`、同じトランザクション。受信箱の証憑は「紐づけ済み」になる）。取消しても紐づけは残す（取消済みの仕訳の証憑として残る。13 の規則のまま）。
- 立替精算が作った仕訳（`sourceKind = expense`）は、取引の画面では取消・訂正できず、明細の画面でも支払に充てた明細は「未処理に戻す」できない（請求書の仕訳と同じ。[決定](../decisions/2026-10-29-invoice-entries-locked.md)）。取引の詳細と明細の「…」は理由と「立替精算を開く」を出す。立替精算の画面の取消・支払の取消だけが `owner: "expense"` を名乗って反対仕訳を作る。
- それでも計上の仕訳が取消済み・訂正済みの立替精算（この規則より前に取り消したものなど）は、支払を拒む（「計上の仕訳 No. n は取消済みです。この立替精算を取り消して出し直してください」）。取消は反対仕訳を飛ばして状態だけ取消済みにする。支払の仕訳が取消済みなら、支払の取消は反対仕訳を飛ばして状態だけ戻す。
- 締め: 利用日・支払日が締め済みなら台帳が拒む（`PERIOD_LOCKED`。画面は「2026/12/31 までは締めています。利用日を開いている日にするか、管理者に締めを戻してもらってください」）。
- ロック: 立替精算の行（id の順に `FOR UPDATE`）→ 支払の行 → 明細の行 → 会計期間の行（`postJournalEntryInTransaction` が取る）。補助科目「立替精算」がまだない（または無効）ときだけ、作る前に advisory lock `expenses` を取る（最初の提出が同時に来ても 2 つ作らない）。
- DB の guard（migration に手書き）: `expense_claim`・`expense_payment` は削除と TRUNCATE を拒む。立替精算は提出の後、状態の列（状態・支払・取消の理由と日時・反対仕訳）しか変わらず、状態は 未払 ⇄ 支払済み と 未払 → 取消済み だけ。支払は取消の列を 1 回だけ設定できる。金額は正、状態と付随の列が食い違わない（CHECK）。バックアップの対象に 2 つのテーブルを足す。
- 監査ログ（entity `expense_claim`）: `expense_claim.submit`（`after` は行）/ `.pay`（1 件ごと。`after: { status, paymentId }`）/ `.unpay`（支払の取消。理由つき）/ `.void`（理由つき）。仕訳の登録・取消は台帳の監査ログ（`journal_entry.*`）が別に残す。監査ログの画面の対象「立替精算」、行の名前は「立替精算 2026/11/05 <内容>」、action の表示名は 提出 / 支払 / 支払の取消 / 取消。
- 入力の検証（Zod。`packages/db/src/schemas.ts`）: 金額は 1 以上 999,999,999 以下の整数、内容は必須で 60 字まで、利用日は暦の日付、立替えた人は有効な利用者、科目は支出に使える科目（`buildSimpleEntry` の検査）、税区分は仕入側。

### 5.3 誰が何をするか

- 提出は経理以上。立替えた人は既定で自分。管理者・経理はほかの有効な利用者を選んで代わりに出せる（業務委託がアカウントを持たないとき、管理者が利用者に足して代わりに出す）。
- 支払う・支払の取消・取消は経理以上。承認の段階はない。

## 6. 画面 `/expenses`

- 入口: 左ナビ「立替精算」（給与の後・決算の前）、スマホは その他 › 立替精算。
- PageHeader: 題名「立替精算」、meta「未払 n 件・x 円」、CTA「立替を出す」（`/expenses/new`）。

- 節「支払済み」: 支払ごとの行（支払日 ・ 立替えた人 ・ 件数 ・ 合計 ・ 口座 ・ 仕訳 No. n ・ 操作「支払の取消」）。直近 20 件、それより前は「さらに表示」。

## 9. 範囲外・あとで決めること

- 承認の段階、立替えた人の本人以外の提出を禁じる設定、利用者ごとの通知。
- 閲覧に証憑・決算書・申告用データを見せること（税理士がそれを要るようになったら、§1 の表に行を足して決める）。
- 報告の中の取引へのリンクを閲覧のときに消すこと（いまは権限の画面になる）。
- 給与が作った仕訳を取引の画面から取り消せないようにすること（立替精算と請求は済み。給与のレーンで決める）。
- IAP の許可リストを画面から変えること（IAM の権限を広げないため、運用の手順のまま）。
