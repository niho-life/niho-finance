# 04. 外部連携

明細の取込（Stripe・銀行・カード）、証憑の読み取り、国税庁の API、e-Tax 向けの書き出しを定めます。根拠と一次情報の URL は [`../research/integrations.md`](../research/integrations.md)。

## 0. 方針

| 連携 | v1 | v2 以降 |
| --- | --- | --- |
| Stripe（platform・拠点） | API で balance transaction を取り込む。読み取り専用の制限付きキー | Organizations の組織キーに一本化、Reports API で月次の確定照合 |
| 銀行 | CSV 取込（銀行別アダプタ＋汎用） | GMO あおぞらネット銀行の API（private access） |
| クレジットカード | CSV 取込 | — |
| 現金・役員立替 | 手入力 | — |
| 証憑 | 手入力のメタデータ | LLM による読み取り＋検証層 |
| 取引先の登録番号 | 手入力 | 国税庁 Web-API で照合、月次で再照合 |
| 申告 | — | 財務諸表 CSV（HOT010）・勘定科目内訳明細書 CSV（HOI010）の書き出し |
| 書き出し | freee / 弥生形式 CSV、beancount、証憑 zip | — |

## 1. Stripe

### 1.1 アカウントの構造

- 既存の `niho-platform`（Connect のプラットフォーム）と `niho-kamakura`（OAuth で接続した Standard の連結アカウント）は会社名義だが、現在の事業主体（別の法人）の名義。日本で本人確認済みのアカウントは事業形態や法人を編集で変えられない。
- 決定（[D4](../decisions/2026-10-28-stripe-new-corporate-account.md)）: NIHO株式会社の法人アカウントを新設し、NIHO アプリの決済をその法人アカウントに移す。移転の計画（platform の作り替え、連結アカウントの再接続、顧客と決済手段のコピー、Webhook と鍵の再発行）は niho-app 側の Epic で扱う。
- 本システムが帳簿に入れる Stripe の口座は、新しい法人アカウントと、その Connect で会社が運営する拠点のアカウントだけ。既存アカウントの履歴は旧事業主体の帳簿であり取り込まない。
- 会社のアカウントが複数になる場合は Stripe の Organizations（最大 75、統合レポート、組織 API キー `sk_org` ＋ `Stripe-Context`）で束ね、帳簿の取込キーは組織の制限付き（読み取りのみ）キー 1 本にする。
- 自社拠点の application fee は 0（[D5](../decisions/2026-10-28-own-spot-application-fee-zero.md)）。他のホストの連結アカウントは取り込まず、platform 側の `platform_earning` だけが会社の売上。

### 1.2 取り込む単位

- 一次データは balance transaction（`amount` = 総額、`fee`、`net`、`available_on`、`created`、`reporting_category`、`source`）。分類は `type` ではなく `reporting_category` を使う。
- `balance_transaction_id` を `WalletTransaction.externalId` にして冪等に upsert し、生 JSON を `raw` に残す。
- 1 件の balance transaction から明細を 2 行作る: 総額の行（`charge` / `refund` / `dispute` など）と手数料の行（`fee` 相当。`fee` が 0 なら作らない）。`reporting_category=fee`（Billing・Tax・Radar・消費税の調整）は手数料だけの行。
- 日付は `created`（JST の暦日）を明細の日付にし、UTC の日付も保持する（Stripe の月次の適格請求書は UTC の月で締まる）。

| reporting_category | 明細 | 既定の仕訳（ルールで生成） |
| --- | --- | --- |
| `charge` | +総額 / −手数料 | Stripe 残高 / 売上高、支払手数料 / Stripe 残高 |
| `refund`、`refund_failure` | −総額（手数料の返還があれば +） | 売上高 / Stripe 残高 |
| `dispute`、`dispute_reversal` | −金額、−紛争手数料 | 雑損失 または 売上高 / Stripe 残高 |
| `fee`（月次調整・Billing・Tax） | −手数料 | 支払手数料 / Stripe 残高 |
| `payout`、`payout_reversal` | −入金額（取消は +） | 普通預金 / Stripe 残高（口座間振替。銀行の入金明細と照合） |
| `platform_earning`、`platform_earning_refund` | +手数料（platform 側） | [09 D5](09-decisions.md) の決定に従い、自社拠点分は内部取引 |
| `transfer`、`topup`、`risk_reserved_funds` 等 | 金額どおり | 内容ごとに手で登録（件数は少ない） |

### 1.3 手数料の消費税

- Stripe の手数料は消費税の課税対象（Visa / Mastercard は 2026-04-01 以降、その他の決済手段は以前から）。Stripe（ストライプジャパン株式会社）は適格請求書発行事業者で、月次の適格請求書がダッシュボードに翌月 10 日までに出る。
- 手数料の行は「税抜の手数料」と「消費税額」に分けて保持する（`reporting_category=fee` の行は `gross` が税抜、`fee` が税額）。取引時点の税額と請求書での端数処理の差は、翌月に `JCT adjustment` の行で調整される。
- 税区分は `purchase_10`。仕入税額控除の根拠は Stripe の月次請求書で、毎月ダウンロードして証憑（`invoice_in`）に保存する。

### 1.4 入金の照合

- 日本のアカウントは日次の自動入金がなく、手動・週次・月次。入金照合レポートは自動入金だけが対象なので、入金スケジュールは自動（週次または月次）にする。
- `payout` の明細と銀行の入金明細を、金額と到着日（±5 日）で結んで口座間振替にする。payout に含まれる balance transaction は `payout=po_xxx` で閉じ、残高のロールフォワード（前回残高 + 取込 = 現在残高）で取りこぼしを検知する。

### 1.5 同期と確定

- 日次ジョブ `stripe-sync`: 前回のカーソル（`created` と最後の ID）から `balance_transactions.list` を新しい順にページングし、`available_on` が未来のものも取り込んで `pending` を表す。
- 月次の確定（v2）: Reports API（`balance_change_from_activity.itemized` と `payout_reconciliation.itemized`、タイムゾーン UTC）を live キーで実行し、取り込んだ明細の合計と突き合わせる。差異はジョブの失敗として通知する。
- Webhook は v1 では使わない（順序保証がなく、API 全件取得で足りる）。即時性が要るようになったら `payout.reconciliation_completed` と `charge.*` だけ受ける。
- レート制限: 本番 100 req/s。日次の全件取得は数百件なので問題にならない。

### 1.6 Stripe Invoicing（受託の請求・v2 任意）

- Stripe の請求書は、登録番号（`jp_trn`）・税率ごとの対価と税額・端数処理を設定すれば適格請求書として使える（公式ガイド。全項目が自動で入るわけではない）。
- 本システムの請求書モジュールが主（銀行振込・納品書・見積書・写しの保存）。カード払いを受けたい相手にだけ Stripe の支払いリンクを添える。

## 2. 銀行

### 2.1 直接つなげる銀行

| 銀行 | 自社口座への直接接続 | 要点 |
| --- | --- | --- |
| GMO あおぞらネット銀行（法人） | 可（private access） | 標準 API 28 種が無償（口座一覧・残高・入出金明細・振込入金明細・振込・バーチャル口座・Webhook 等）。sunabar（API 実験場）は口座保有者なら審査なし。契約までの目安は 2 か月以内（申込 → 審査 → 契約 → 接続テスト） |
| 三井住友銀行 | 可（Web21 サーバー接続） | エキスパートタイプの契約と審査。料金は非公開 |
| 楽天・三菱 UFJ・みずほ | 外部サービス会社（電子決済等代行業者）経由が前提 | 個社の直結は想定されていない |
| ドコモ SMTB ネット銀行（旧 住信 SBI） | 個別相談 | 入出金明細 API の公開仕様・料金は未確認 |
| PayPay 銀行 | 法人向け API 連携あり（OAuth 2.0） | 稼働まで最短 7 週間。条件は要問い合わせ |

推奨は GMO あおぞら（[09 D3](09-decisions.md)）。口座開設と接続審査の申込を設立直後に出し、v1 の間は CSV、v2 で API に切り替える。

### 2.2 CSV の取込（v1）

銀行別のアダプタ（列の自動判別、cp932 / UTF-8 / BOM、符号付き金額か入出金の別列か、日付の形式、和暦）を作り、実ファイルを架空の値に置き換えたフィクスチャでゴールデンテストを持つ。

| 形式 | 列（調査時点。実ファイルで確定） |
| --- | --- |
| GMO あおぞら 全銀 CSV | ヘッダ（口座・取引前残高）/ データ（勘定日〔和暦 YYMMDD〕・起算日・入払区分・取引区分・取引金額・振込依頼人名・仕向銀行・摘要・EDI）/ トレーラ（件数・合計・取引後残高） |
| GMO あおぞら 当社 CSV | 項目定義は未確認。実ファイルで確定 |
| ドコモ SMTB（住信 SBI） | 日付, 内容, 出金金額(円), 入金金額(円), 残高(円), メモ。`YYYY/MM/DD`、cp932 |
| 楽天銀行 | 取引日, 入出金(円), 取引後残高(円), 入出金内容。`YYYYMMDD`、符号付き |
| PayPay 銀行 | 操作日（年・月・日）、操作時刻、取引順番号、お支払金額、お預り金額、摘要、残高 |
| ゆうちょ Biz ダイレクト | 取引日, 入出金区分（受入 / 払出）, 取引内容, 送金人名等, 受入明細番号, 取扱口数, 取引金額, 現在高, EDI |
| 汎用 | 日付・摘要・金額（または出金・入金）・残高 の列を画面で対応づけ、口座に保存 |

- 内部の形は `WalletTransaction`（日付・起算日・符号付き金額・取引後残高・相手名・摘要・行ハッシュ・生データ）に統一する。
- 取引後残高の連続性（前行の残高 + 金額 = 当行の残高）で取りこぼしと重複を検知する。

### 2.3 GMO あおぞら API（v2）

- `GET /accounts/transactions`（`accountId`, `dateFrom`, `dateTo`, `nextItemKey`）。`itemKey`（マイクロ秒のタイムスタンプ）を冪等キーにする。`transactionType` 1 = 入金 / 2 = 出金、`remarks`、`balance`。
- 全銀フォーマットの明細 API もある（取引区分・振込依頼人名カナ・EDI）。
- 認証は OAuth 2.0 + OpenID Connect。キーは Secret Manager。sunabar には Webhook がないので、本番の通知は別途確認する。
- バーチャル口座（振込入金口座）は無料で発行でき、受託の請求ごとに口座を分ければ入金の消込が自動になる（v2 の選択肢）。
- 同期の仕様（認可とトークンの置き場、取得の期間、CSV との重なり、残高の照合、再接続）は [19](19-bank-api.md)。

## 3. クレジットカード

- 法人カードの明細は CSV（JCB は CSV / OFX、AMEX は CSV / QIF、三井住友・楽天は CSV）。列はカード会社の実ファイルで確定し、銀行と同じアダプタの仕組みで取り込む。
- API を公開している法人カード（UPSIDER・paild）は会計 SaaS 向けの連携だけで、個社の開発者 API は見当たらない。
- カードの口座は負債（未払金）に紐づけ、引落は銀行明細との口座間振替で消す。

## 4. 証憑の読み取り（v2）

- 読み取りは provider を抽象化し、第一候補は LLM の vision（画像 → JSON Schema で強制: 日付・合計・税率別の対価と税額・発行者名・登録番号・但し書き）。Google Document AI（Expense Parser）と Azure Document Intelligence（receipt、日本語対応）は同じゴールドセットで比較し、必要なら二重チェックに使う。
- 読み取り後の検証層を必須にする: 税率別の合計の突合、登録番号の形式（T + 13 桁）と法人番号のチェックデジット、国税庁 API での照合、日付と金額の妥当性、重複（同じ発行者・日付・金額）。通らないものは「要確認」として受信箱に残す。
- 結果は提案として入力欄に入り、人が確認して保存する。自動で仕訳を確定しない。

## 5. 国税庁 適格請求書発行事業者公表システム Web-API

- アプリケーション ID の取得に審査があるので早めに申請する。数値のレート制限は公表されていないため、10 件ずつのバッチ・キャッシュ・低頻度で使う。
- `Partner.invoiceRegistrationNumber` の照合結果は「取引日時点の登録状況」として保存し、未登録なら仕入税額控除の経過措置の税区分（[03](03-compliance.md)）に回す。
- 全件（毎月）と差分（日次）の一括ダウンロードがあり、ローカルの写しで照合することもできる（再利用条件は要確認）。
- 法人番号のチェックデジット: 下 12 桁について、最下位から数えて偶数桁の和 × 2 + 奇数桁の和 を 9 で割った余りを 9 から引く。

## 6. e-Tax 向けの書き出し（v2）

- 財務諸表は XBRL か CSV（HOT010 Ver.3.0）の選択制。CSV は e-Tax ソフトで XBRL に変換されるので、自前で XBRL を組まない。
- HOT010 は 5 列固定（種別又は勘定科目 / 内容又は金額等 / 行区分 / 階層番号 / 勘定科目コード）。先頭に `A`（BS / PL / NT / SS 等）、`B`（法人名）、`C1` / `C2`（事業年度）。金額はカンマなし、Shift-JIS、JIS 第 1・第 2 水準のみ、ファイル名は `HOT010_3.0_BS.csv` の形。
- 勘定科目内訳明細書は CSV（HOI010 等）か XML。様式ごとに事業年度で版が分かれる。
- `Account` に e-Tax の勘定科目コード・階層番号・行区分を持たせ、公式のコード表（HTML / Excel）から版管理つきで取り込む。出力後は国税庁の「CSV ファイルチェックコーナー」で手動 QA する。
- 申告書本体（別表）の XTX を自作ソフトから送る公開 API はない。申告は e-Tax ソフトまたは税理士のソフトに取り込ませる。国税システムの更改（KSK2）で仕様が段階公開されているので、参照した仕様の URL・更新日・版を記録し、四半期ごとに差分を見る。
- 使える OSS は見つからなかった（個人事業主向けの XTX 出力の試作が 1 件。検査ツールは配布物が不審で使わない）。

## 7. 給与・社会保険（v3）

- 源泉徴収税額表は国税庁が PDF と Excel で公開（CSV なし）。協会けんぽの料率は HTML、保険料額表は PDF。成熟した OSS はない。
- 年 1 回、表を取り込んで版管理する前提で設計する（v3）。

## 9. 要確認（実装前に実物で確かめる）

- GMO あおぞら「当社 CSV」の列、住信 SBI・楽天・PayPay・カード各社の CSV の列（実ファイル）。
- Stripe の手数料の消費税が `fee_details`（type=tax）で分かれて出るか。紛争手数料が同じ balance transaction の `fee` に入るか別行か。
- 現在の 2 アカウントの登録上の事業形態と、法人化で Stripe が名義変更を認めるか（サポートへ書面で確認）。
- 国税庁 Web-API のアプリケーション ID の審査期間と、公表データを自社 DB に保存してよいか。
- Document AI / Azure の円建て料金。
