# 起動時の先回り（DB の接続・IAP の公開鍵）は採らず、起動直後の要求の内訳をログに残す（#82）

- 状況: 画面は最小インスタンス 0 の Cloud Run で動き、インスタンスは待っている要求のために起動する。本番（6c40136）で、インスタンスが落ちた後の 1 回目のホームは TTFB 3,425 ms、Cloud Run の処理時間 2,572 ms だった（2 回目は 395 ms・217 ms）。ログの時刻では、起動から Next.js の準備まで約 1.0 秒、準備から応答まで約 1.4 秒。その要求は proxy の中で、IAP の公開鍵の取得と DB への最初の接続を直列に待つ。そこで #88 で、`instrumentation.ts` の `register` で両方を並行して始める先回りを入れた。
- 計測（本番 8bb0e62、17 分空けた後の 1 回目）: TTFB 5,586 ms、Cloud Run の処理時間 4,603 ms で、先回りなしより約 2 秒遅かった。内訳は次のとおり。
  - インスタンスの起動から Next.js の準備まで 1.39 秒。
  - 準備から proxy に入るまで 2.66 秒。`register` は準備の約 0.5 秒後に呼ばれていた。
  - proxy は 0.56 秒（IAP の検証 202 ms、利用者の照会 356 ms）。
  - 先回りした鍵の取得は 2,293 ms、DB の接続は 2,650 ms かかった。
- 決定: 起動時の先回りは採らない（`instrumentation.ts` を外す）。起動直後の 3 件の要求の内訳（`startup.request`）のログは残す。最小インスタンスは 0 のまま（固定費の上限）。
- 理由: `register` から db パッケージ一式を読み込み、Prisma を初期化すると、その処理が起動直後に走る。1 vCPU の上で、ルートのモジュールの読み込みと CPU を取り合い、モジュールの読み込みの間はイベントループが止まるため、並行のつもりの通信も進みにくい。そのため、1 回目の要求が待つ時間が増えたとみられる。
- 影響: [05 §3.3](../design/05-ui-ux.md)、[`docs/ops/deploy.md`](../ops/deploy.md) §8（ログの見方）。次に詰めるのは、Next.js の準備から proxy に入るまでと描画の部分（モジュールの読み込み量）。月額は変わらない。
