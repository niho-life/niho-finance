# 資金繰りの予測: 線は現預金の合計 1 本・定期取引は仕訳の型・欠ける入力は注記（2026-10-28）

## 状況

Issue #19 で、定期取引と税金の予定から 90 日の残高の線をホームと報告に出す。会社は当面 1 人で、口座は銀行・カード・Stripe（2 アカウント）・現金・役員立替。サブスクの多くはカード払いで、カードの引落しは月 1 回・金額が毎月変わる。Stripe の残高は自動で銀行へ入金される。税金・社会保険の期限（S8 #9）、法人税等の予定額（#14）、請求（#16）、給与（#20 第 2 段）は別のレーンで作っていて、まだ main にない。

## 決定

1. 線は**現預金の合計 1 本**にし、口座ごとの線は描かない。0 円を割る警告も合計で出す。
2. 定期取引 1 件を「口座の科目 ⇄ 科目」の仕訳の型とみなし、現預金への増減を複式で導く（`口座の科目が現預金 ? 金額 : 0` − `科目が現預金 ? 金額 : 0`）。カード払いの定期取引は線を動かさず、カードの引落しは銀行の定期取引（科目: 未払金）として登録する。
3. 起点はホームと同じ日、日付は名目（土日祝でずらさない）。起点の日に発生する定期取引は数えない。
4. 欠ける入力は線に推定で埋めず、「入っていないもの」に注記する。未接続（`null`）と 0 件を区別する。金額のない納付の期限は線を動かさず印だけ付ける。期日を過ぎた未入金は入れず、期日を過ぎた未払は起点の翌日に出す。
5. 予測は保存せず毎回導出し、定期取引から仕訳を自動で登録しない。

## 理由

- 口座ごとに描くと、Stripe から銀行への入金のような現預金の中の移動を全部登録しない限り「銀行が 0 を割る」誤った警告が出る。1 人の会社が見たいのは「会社のお金が足りるか」で、合計で足りる。
- 仕訳の型として扱えば、カード払い（未払金が増えるだけ）・カードの引落し（現預金が減る）・Stripe の入金（現預金の中の移動）が同じ式で正しく出て、カード払いと引落しを二重に数えない。カードの引落しの金額は毎月変わるので、利用日に出金とみなすより、引落しを概算で登録する方が引落し日の残高（0 を割るかどうか）を正しく見られる。
- 起点の値をホームの現預金と一致させると、線の始まりを数字で確かめられる。起点の日の分は仕訳か取り込む明細に入るので、数えると二重になり得る。
- 欠けた入力を推定で埋めると線が正しそうに見えて判断を誤る（Q > D）。お金が足りなくなる側は保守的に（未払は早めに、期日を過ぎた未入金は入れない）見る。
- 予測は帳簿ではない。仕訳の自動登録は明細の取込（S4・S5）と二重になり、帳簿の正しさを崩す。

## 影響

- カード払いのサブスクを多く持つ間は、カードの引落しを定期取引に登録しないと線が楽観的になる。カードに未払があって引落しの定期取引がなければ注記で知らせる。
- 未入金の請求は請求（#16）の残高から繋いだ。税金・社会保険の金額は #14・#20 が main に入ってから、未払の請求は受け取る請求書の支払期日ができてから `loadCashflowInputs`（`packages/db/src/recurring.ts`）で繋ぐ。予測の関数（`packages/reports/src/cashflow-forecast.ts`）は変えない。
- 明細の推定（S5 #6）は同じ `RecurringItem` を読む。定期取引の列は S1 の schema のまま足していない。
