# 役割は 管理者・経理・閲覧 の 3 つ。書き込みは各 Server Action の入口、画面は proxy で絞る（#21）

- 状況: v1 は IAP を通った人なら誰でも何でも書けた。v3 で社員・業務委託（経理）と税理士（閲覧）を足す。Server Action は 13 ファイル・約 100 本、画面は 51 枚あり、各レーンが所有している。App Router のレイアウトは画面の移動で再実行されないので、レイアウトでの検査は画面の制限にならない。最初の管理者のメールは公開リポにも migration にも書けない。
- 決定（2026-10-29）: 役割は S1 の `user_role`（owner / accountant / viewer。表示は 管理者 / 経理 / 閲覧）のまま。経理は「締め（期間の状態を変える操作）と、事業所・会計期間・証憑の規程・利用者・初期設定」を除く全部、閲覧は報告と帳簿の書き出し（freee・弥生・beancount）だけ。検査は (1) 全 Server Action の最初の 2 文 `const denied = await authorizeAction(最低の役割); if (denied) return denied;` で、(2) route の入口で、(3) 画面は `apps/web/proxy.ts` で閲覧と未登録を許す path に絞る。拒否は何も書かず、監査ログにも残さない。`app_user` が空のときは最初に書き込んだ人を管理者として登録する。
- 理由: 入口の検査は 1 関数 2 行で各レーンのファイルを最小限しか触らず、入力の検証より前に断れ、網羅テストで入れ忘れを止められる。画面の制限を各ページに書くと 51 ファイルに広がり、レイアウトでは移動のたびに検査されない。proxy は全要求の前に走るので 1 ファイルで済む（本当の検査は (1)(2) で、proxy は早めに断る層）。最初の管理者は、いまの IAP の許可リストが代表 1 人なので、最初に書いた人が代表になる。
- 影響: [23](../design/23-users-and-expenses.md)（新規）、[01 §8](../design/01-domain-model.md)、[06 §3.2](../design/06-architecture.md)、[`docs/ops/deploy.md`](../ops/deploy.md) §5（利用者を足す順番と最初の管理者）。新しい Server Action は `authorize` を通さないと単体テストが落ちる。閲覧に証憑・決算書を見せるかは、税理士が要るようになったら決める。
