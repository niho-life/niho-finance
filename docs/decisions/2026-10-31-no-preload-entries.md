# Next.js の起動時の全ページの先読みを切る（#82）

- 状況: 画面は最小インスタンス 0 の Cloud Run で動き、インスタンスは待っている要求のために起動する。インスタンスが落ちた後の 1 回目のホームの TTFB は、測るたびに 3.4 秒・5.6 秒・7.3 秒と大きく揺れた（2 回目以降は 0.3〜0.5 秒）。先回りを外した版（a34a3ea）の 1 回目の内訳は次のとおり（ログの時刻と `startup.request`）。
  - インスタンスの起動から Next.js の準備まで 1.18 秒。
  - 準備から proxy に入るまで約 1.15 秒。
  - IAP の公開鍵の取得を含む署名の検証が 3,035 ms。
  - DB での利用者の照会が 578 ms。
  - 描画が約 0.6 秒。
  - 外向きの通信は VPC を通らない設定（private-ranges-only）で、経路に原因は見当たらない。
- 原因の見立て: Next.js は既定（`preloadEntriesOnStart: true`）で、準備ができた直後に全ページのモジュールを背後で読み込む（`next-server.js` の `unstable_preloadEntries`）。このアプリはページが多く、PDF の生成などの重いモジュールもある。読み込みは同期で CPU を使い、その間イベントループが止まる。1 回目の要求の通信（IAP の鍵の取得・DB の接続）は先読みが終わるまで進みにくく、要求の着く時刻と先読みの進み具合で待ちが揺れる。
- 決定: `experimental.preloadEntriesOnStart: false` にする。1 回目の要求には、その要求に要るモジュール（proxy とその画面）だけを読む。月額は変わらない（最小インスタンスは 0 のまま）。
- 引き換え: ほかの画面は、そのインスタンスで初めて開いたときにモジュールを読むので、その 1 回だけ少し遅くなる。
- 確認: 配備後、同じ条件（17 分以上空けた後の 1 回目）で TTFB と内訳を測り、#82 に記録する。効果がなければ既定に戻す。
- 影響: [05 §3.3](../design/05-ui-ux.md)、`apps/web/next.config.ts`。
